# IGRIS-C SDK — ROS 2 workspace

This directory is a ready-to-build colcon workspace containing one
package: `src/igris_c_sdk_public/`. The folder is named after the
public deliverable, but the package itself is declared in `package.xml`
as `igris_c_sdk` — DDS type ids must match what the SDK bridge
publishes (`igris_c_sdk::msg::*`) for wire-format interop, so the
package name is locked.

The package bundles, in a single fresh-build:

- `msg/`, `srv/` — interface definitions (regenerated by
  `rosidl_generate_interfaces` in the consuming workspace).
- `src/*.cpp` — ROS 2 example client nodes (subscriber, publisher,
  service client, GUI client, walk-mode keyboard, hand init).

> **Topic layout:** these nodes do not take `--dds-topic-naming`. On the ROS 2 lane rmw
> always prepends `rt/`, so there is nothing to select — the robot must be on
> `igris_c.network.transport: ros`. The cyclonedds and Python examples do take the flag;
> see the root README's [Topic layout](../README.md#topic-layout).

## Quick test (build in place)

> Run this from a shell with **no Python environment active** (no `pixi shell`, no venv).
> CMake's `FindPython3` searches `$CONDA_PREFIX` / `$VIRTUAL_ENV` before the system paths,
> and ROS 2's interface generators need the system Python. To build from inside one anyway,
> pass `--cmake-args -DPython3_EXECUTABLE=/usr/bin/python3`.

```bash
cd <deliverable>/ros2
colcon build
source install/setup.bash
ROS_DOMAIN_ID=5 ros2 run igris_c_sdk ros_lowstate_listener \
    --ros-args -p robot_namespace:=igris_c_<your_robot_id>
```

## Configuration

Every example node takes two knobs that pair it with a specific
robot bridge:

### `ROS_DOMAIN_ID` — DDS domain (environment variable)

ROS 2 binds the DDS domain at `rclcpp::init` (participant creation)
time, so it cannot be a node parameter. The examples honour the
standard `ROS_DOMAIN_ID` env var:

```bash
export ROS_DOMAIN_ID=5
ros2 run igris_c_sdk ros_lowstate_listener
```

…or inline per invocation:

```bash
ROS_DOMAIN_ID=5 ros2 run igris_c_sdk ros_lowstate_listener
```

Defaults to `0` when unset. Match this to the bridge's
`ROS_DOMAIN_ID` / SDK CLI domain id.

### `robot_namespace` — topic / service prefix (ROS parameter)

Every example reads the ROS parameter `robot_namespace` (default `""`)
and prepends it to the SDK topic names (e.g. `/<ns>/lowstate`). ROS topics carry no `rt/`
segment: rmw adds it when mangling to DDS, so writing it here would produce `rt/<ns>/rt/<topic>`
on the wire.
Match this to the bridge's `user_suffix` (typically
`igris_c_<robot_id>`):

```bash
ros2 run igris_c_sdk ros_lowstate_listener \
    --ros-args -p robot_namespace:=igris_c_<your_robot_id>
```

Or in a launch file:

```python
Node(
    package='igris_c_sdk',
    executable='ros_lowstate_listener',
    parameters=[{'robot_namespace': 'igris_c_robot1'}],
)
```

Leave it empty to talk to topics at the root (`/lowstate`).

### Both together

```bash
ROS_DOMAIN_ID=5 ros2 run igris_c_sdk ros_lowstate_listener \
    --ros-args -p robot_namespace:=igris_c_robot1
```

## Discovery when multicast does not reach the robot

Symptom: `ros2 topic list` shows nothing from the robot, or shows only a
few topics while the robot itself lists them all. `ROS_DOMAIN_ID` is
correct and `ping <robot>` works.

Cause: DDS discovery uses the multicast group `239.255.0.1`, and an
access point does not forward it from its wireless clients to the wired
segment. A robot reachable ONLY over Wi-Fi is therefore invisible to a
wired client even on the same subnet — a successful ping says nothing
about multicast. A robot that also has a working wired link does not
need any of this: multicast reaching it in one direction is enough for
discovery to complete, and everything after that is unicast. Which case
you are in can change when a cable is plugged in or drops, so go by the
symptom rather than the topology.

Fix: `fastdds_peers.xml` in this directory makes discovery go out
unicast instead. Edit the one address in it to the robot's IP, then:

```bash
export FASTRTPS_DEFAULT_PROFILES_FILE=$PWD/fastdds_peers.xml
export ROS_DOMAIN_ID=<robot's igris_c.network.domain_id>
ros2 daemon stop
ros2 topic list
```

Three things that are easy to get wrong:

- **`ros2 daemon stop` is required.** A daemon started without the
  profile has cached its discovery results, and the CLI asks that
  daemon — so the profile appears to do nothing until it is restarted.
- **The variable is `FASTRTPS_`, not `FASTDDS_`.** Fast DDS was
  formerly Fast RTPS and kept the old name here;
  `FASTDDS_DEFAULT_PROFILES_FILE` is not read at all.
- **`ROS_STATIC_PEERS` is not a substitute.** It sets the address but
  cannot raise the participant-id range, so it finds only the first few
  processes the robot happens to have started — which ones those are
  changes on every restart. Measured against one robot: this file alone
  listed 30 topics, `ROS_STATIC_PEERS` alone listed 5, and the two
  together listed 30 — so it adds nothing here. Unset it.

The file sets `maxInitialPeersRange` to 32 for exactly that reason (the
Fast DDS default probes participant ids 0-3 only), and deliberately
carries no `<port>`: Fast DDS derives the discovery port from
`ROS_DOMAIN_ID` at run time, so the same file works on any domain.

This is a client-side workaround, and the robot's wired link is the real
fix: with it up, multicast works and none of this is needed — measured
by sending the same packet out each of the robot's interfaces to a wired
client, where the wired NIC's arrived and the Wi-Fi NIC's did not.

### Worked example

Everything an example node needs, in one line. Keep the file somewhere
stable rather than editing the copy in the deliverable, so a reinstall
does not overwrite the address:

```bash
mkdir -p ~/.config/igris_c
cp fastdds_peers.xml ~/.config/igris_c/
# edit ~/.config/igris_c/fastdds_peers.xml: set <address> to the robot's IP
ros2 daemon stop
```

Then, for a robot on domain 5 with namespace `igris_c_IG01`:

```bash
FASTRTPS_DEFAULT_PROFILES_FILE=$HOME/.config/igris_c/fastdds_peers.xml \
ROS_DOMAIN_ID=5 \
ros2 run igris_c_sdk ros_sensor_viewer --ros-args -p robot_namespace:=igris_c_IG01
```

The same two variables prefix every other example — only the node name
and the namespace change:

```bash
FASTRTPS_DEFAULT_PROFILES_FILE=$HOME/.config/igris_c/fastdds_peers.xml \
ROS_DOMAIN_ID=5 \
ros2 run igris_c_sdk ros_lowstate_listener --ros-args -p robot_namespace:=igris_c_IG01
```

Export them instead of prefixing each command if you are running several
in a row. `ros2 daemon stop` is needed once per shell session, after the
variables are set — not before every command.

## Host network tuning (camera image streams)

Required on this machine before subscribing to the camera image topics
(`/<ns>/sensor/*`). The control topics (`lowstate`, `lowcmd`, …)
are small and need none of this.

```bash
cd <deliverable>/ros2
./setup_client_network.sh
```

An image frame is far larger than one UDP datagram, so Fast DDS sends
~64KiB datagrams and the IP layer splits each into ~40 Ethernet
frames. This host has to hold every piece in a kernel reassembly pool
until the datagram is complete — one missing piece discards all of
them. Two distribution defaults are too small for that:

- `net.core.rmem_default` (208KiB) is the receive buffer a socket gets
  when it does not request a size, which is what Fast DDS does by
  default.
- `net.ipv4.ipfrag_high_thresh` (4MiB) is the reassembly pool, about
  190ms of a 21MB/s stream. Incomplete datagrams squat in it for
  `ipfrag_time` (30s), so the pool hits its ceiling and evicts
  datagrams that were about to complete.

Untuned, the symptom is not a slow stream but a silent one: the
control topics and the IMU keep working (single-datagram messages),
while every image topic sits at exactly 0 Hz even though the interface
counters show the data arriving. Check it with:

```bash
nstat -az | grep IpReasm    # IpReasmOKs should dominate IpReasmFails
```

The script writes `/etc/sysctl.d/99-igris-c-sdk-client.conf`, so the
values survive a reboot. Delete that file to revert.

## Use in your own workspace

Drag the package folder into your workspace `src/`:

```bash
cp -r <deliverable>/ros2/src/igris_c_sdk_public ~/my_ws/src/
cd ~/my_ws && colcon build
source install/setup.bash
# In your own package's CMakeLists.txt:
#   find_package(igris_c_sdk REQUIRED)
#   ament_target_dependencies(my_node rclcpp igris_c_sdk)
# In your node:
#   #include "igris_c_sdk/msg/pdu_state.hpp"
```

## Pre-built C++ usage (separate)

For direct C++ usage of the bundled SDK static library
(`publisher.hpp` / `subscriber.hpp` / Cyclone DDS in
`igris_c_sdk::igris_c_sdk`), see `<deliverable>/cyclonedds/` — that
tree carries `include/`, `lib/`, `thirdparty/`, the standalone CMake
config, plus a `CMakeLists.txt` that builds the example clients. The
ROS 2 package here is independent and does not require the C++ tree.
